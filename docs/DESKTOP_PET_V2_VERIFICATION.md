```sh
npm run dev
WAGECLAW_DEV_SERVER_URL=http://127.0.0.1:5174 npm run electron
npm run check
WAGECLAW_QA_URL=http://127.0.0.1:5174 node scripts/verify-lite.mjs
WAGECLAW_QA_URL=http://127.0.0.1:5174 node scripts/verify-pet.mjs
WAGECLAW_QA_URL=http://127.0.0.1:5174 node scripts/verify-pet-features.mjs
WAGECLAW_QA_ELECTRON=1 WAGECLAW_QA_URL=http://127.0.0.1:5174 node scripts/verify-pet-motion.mjs
```

端口按开发服务实际输出调整。受限环境（容器、沙箱）里追加 `WAGECLAW_QA_NO_SANDBOX=1`，脚本会给 Electron 补上 `--no-sandbox`。

**注意超时**：`npm run check` 和 `git commit`（触发 husky pre-commit 的 `lint && typecheck && test`）都是链式 npm 命令，四步串起来常超过 120s，会被运行环境掐断并留下 **Exit 137 (SIGTERM)**，日志只到前半段。这不是代码问题 —— **给这次命令显式加长超时（300s）重跑即可**，不要因此改代码，也不要加 `--no-verify` 跳过钩子。

**注意退出码**：三个脚本末尾都会启动真实 Chrome，Chrome 自身的 code-sign clone / RLZ 清理写入在受限环境里会被拦截，导致进程退出码非 0。要判断成败请看 stdout 末尾的结论行，不要只看退出码。

浏览器 `?view=pet-preview` 可预览形象和文案，但不代表原生桌面效果。

## 2026-09-18：夏季作息、形象进化、悬停浮层与播报提速

### 夏季作息（两套作息按日期区间切换）

- 原因：原有模型只有单一 `startTime`/`endTime`，`overrides` 只存「某天算不算工作日」，无法表达「按日期区间换作息」。
- 调整：新增 `summerFrom`/`summerTo`（`MM-DD`，每年自动重复，支持跨年区间）与 `summerStartTime`/`summerEndTime`；新增 `activeShift()` 作为唯一判定入口，收入进度、下班倒计时、播报节点、桌宠阶段共用同一结果。出厂默认常规 08:30–17:30、夏季 05-01～10-01 的 08:30–18:00；区间留空即全年使用常规作息。
- 边界：区间含起止当天；半填区间在清洗阶段整体丢弃，不会留下半个配置。

### 午休口径（用户拍板）

- 用户明确「午休不暂停，按工作计入」。核查确认这本就是既有行为：源码中不存在任何午休暂停逻辑，班次始终是单段连续的。
- 实测（08:30–18:00、月薪 18000）：每分钟增量从 08:30 到 18:00 恒为 ¥1.4354，跨 12:00–13:30 无折点。
- 为防止回退，新增两条回归测试固定该行为，并把设置面板、主面板脚注与各 README 的文案统一为「午休照常计入工时（不扣除、不暂停）」。

### 五套形象与十阶进化

- 原因：旧版十阶由「怨气值」驱动，与 V2「不做养成负担」的红线冲突。
- 调整：改为由**当天班次进度**驱动，`阶段 = clamp(floor(已过比例 × 10) + 1, 1, 10)`。上班瞬间第 1 阶、下班瞬间第 10 阶；休息日与未上班时间固定第 1 阶，下班后固定第 10 阶。因为走 `activeShift()`，夏季作息自动跟随。每 30 秒校准一次，不做逐秒重绘。
- 素材：卡皮巴拉／懒猫／懒狗／老实牛各用一张 2880×288 合图（10 格 × 288px，按 `(level-1)*288` 切片）；怨气团用 10 张独立 512×512 图。两条路径由 `petAssets.ts` 归一成同一 `PetFrame`，Canvas 侧无分支。
- 切换入口：设置面板下拉、托盘「切换形象」子菜单、`?view=pet-preview` 预览页。选择写入 `pet.style`，重启保留，并兼容旧版顶层 `petStyle`。

### 悬停信息浮层

- 新增 `?view=hover` 视图（280×158 独立透明窗口），按需创建、无内容即销毁。
- 鼠标进入桌宠可点击像素区时建窗，离开 320ms 后销毁；浮层自身可悬停，移入会取消这次销毁。打开面板或开始拖动时立即销毁。
- 定位优先桌宠上方；有气泡占位时让到下方；越界时按工作区夹取。

### 春节与年终奖改为每年重复（用户拍板）

- 原因（真 bug）：`springCountdown` / `bonusCountdown` 用带年份的完整日期（`2027-02-04`）做一次性比较，日期一过就永久停在 `started` / `past`，2028 年也不恢复。连带影响：悬停卡「距离年终奖」永久显示「已过」，`broadcast.candidates()` 按 `state === 'upcoming'` 过滤，两条播报永久消失。对照 `paydayCountdown` 会正确滚到下一月，可见这是实现疏漏而非设计。
- 调整：`springStart` / `springEnd` / `bonusDate` 改存 `MM-DD`，每年重复，与发薪日、夏季作息口径一致。新增 `nextMonthDay()` / `previousMonthDay()` / `inMonthDayRange()` 三个纯函数；`activeShift()` 的跨年区间判断也改走 `inMonthDayRange()`，不再重复写一遍比较。`isWorkday()` 的假期判断同步改成按月-日匹配。
- 滚动口径：假期结束后直接滚到下一年的同一天（`ended` 状态因此不再产生，已从状态表和文案里移除）；平年的 2 月 29 日顺延到 2 月 28 日，与发薪日的月末夹取一致。
- **默认值已由用户确认，不是待办**：春节 `springStart` 为 `02-04`，`springEnd` **有意留空** —— 用户明确选择「只放 2/4 当天」，因此 2/4 是唯一休息日，2/5 起正常上班。这是确定的口径，不是缺参数，后续不要再当作待补项追问。设置面板的提示文案「只填开始日期时，仅将当天记为休息日」已与此一致。
- **迁移已在真实存档上验证通过**：用户那个跑了近 4 小时的开发实例是在改动前启动的，主进程加载的是旧的 `core.cjs`，所以它的存档一直停留在旧格式 —— `springStart: "2027-02-04"`、`bonusDate: "2027-02-03"`，还带着旧布尔 `bonusReceived: false`。用这份真实存档当 profile 启动一次，内存与磁盘都收敛成了 `02-04` / `02-03` / `bonusReceivedAt: ""`，旧字段不再残留。这条比单测更有说服力：单测喂的是构造数据，这里喂的是真实文件。
- **午休口径已由用户确认**：12:00–13:00（夏季 12:00–13:30）**计入工时**，因此班次按 `08:30 → 17:30` / `08:30 → 18:00` 单段连续计时，一天的计价工时为 **9h（常规）/ 9.5h（夏季）**，不是 8h。模型里不存午休起止时间（`Shift` 只有 `startTime` / `endTime`），这是有意设计。
- 年终奖「已收到」：字段由布尔 `bonusReceived` 改为日期 `bonusReceivedAt`，只在**本轮发放周期**内生效（发放日当天起 30 天宽限期）。这样跨年后标记自动作废，不会在下一年发放日当天误报「已收到」；旧档的布尔标记无法判断属于哪一轮，迁移时直接作废由用户重新标记。
- 迁移：`migrateMonthDay()` 在清洗阶段把旧档的 `2027-02-04` 收敛成 `02-04`，无效值落成空字符串（未设置），不需要用户手动改存档。
- 界面：设置面板三个日期输入由 `<input type="date">` 改成 5 位文本输入（与夏季作息一致），填完整日期会被校验拦下并提示「格式为 月-日」；卡片脚注改成「每年 02.04 起」；「标记已收到」按钮改走 `markBonus()` 写入当天日期。

### 窗口加载失败不再白屏 + 修掉被拦掉的整页刷新

**现象**：双击桌宠后窗口打开但一片空白。

**根因**：该实例是开发模式，前端由 Vite 开发服务器提供。开发服务器停掉后，桌宠窗口（服务器还在时加载的）画面正常，但双击新建的面板窗口此时才去 `loadURL('http://127.0.0.1:5173?view=main')`，连接被拒。Chromium 停在自己的错误页，实测该窗口 `url()` 为 `chrome-error://chromewebdata/`、`body.innerHTML` 长度为 **0** —— 就是那片空白。打包版从 `dist/` 读取，不受影响。

**改动**：

- `loadRenderer` 的 `loadURL` 失败分支不再只打一行日志，而是渲染一张说明页：写明开发服务器地址、让用户先 `npm run dev`、并给出「关掉这个窗口重新双击桌宠」的恢复动作；打包版则提示重新安装。原来只有一个空白窗，属于哑失败。
- 顺带修掉 `will-navigate` 的**无条件 `preventDefault()`**：它把渲染层发起的所有导航都拦掉了，包括 Vite 的 `location.reload()`，导致开发时整页刷新被静默阻止、页面卡在「导航中」。改为只拦非同源导航。
- 开发模式下失败前先**静默重试**（5 次 × 700ms）：`npm run dev` 常常比 Electron 慢几秒，窗口先到就会撞上连接被拒，这时自愈比报错更合适。只对连接类错误重试（`ERR_CONNECTION_REFUSED` / `RESET` / `FAILED` / `CLOSED` / `TIMED_OUT` / `EMPTY_RESPONSE` / `ADDRESS_UNREACHABLE` / `NAME_NOT_RESOLVED`），其它错误（如 `ERR_ABORTED`）重试只会打转，直接落到说明页。打包版不重试。

**验证**（临时脚本，验完即删）：

- 死端口实例：窗口内容由空变为「这个窗口没能加载内容 … 先在项目里运行 npm run dev」。
- 真实双击流程：服务器在 → 引导完成桌宠渲染 → 杀掉服务器 → 双击桌宠 → 新建的 `view=main` 窗口显示上述提示，不再是白屏。
- 重试策略：先确认 `loadURL` 拒绝时错误对象带 `code` / `errno` / `url`，实测 `code === 'ERR_CONNECTION_REFUSED'`、`errno === -102`（重试集合就是按这个字段匹配的；万一字段缺失，`has(undefined)` 为假会直接走说明页，退化成修复前的行为，不会更糟）。再跑两个时序：服务器比窗口晚 1.5 秒上线 → 窗口标题变成 `RECOVERED`、地址停在开发服务器，**没有**走到说明页；服务器全程不上线 → 重试耗尽后正常落到说明页（标题「忍了吧 · 加载失败」）。两个场景都通过。
- 导航边界：修复前 `location.reload()` 被拦（window 标记存活），修复后刷新成功（标记被清掉）；同时 `location.href = 'https://example.com/'` 仍被拦住，窗口 URL 停留在本机 —— 没有开出跳外站的口子。
- 回归：`verify-pet.mjs`（含真实双击开面板 + 20 轮开关面板，每轮都等 `today-income` 出现）、`verify-pet-features.mjs`（5 段全过）、`verify-pet-motion.mjs`、`verify-lite.mjs` 全部通过；lint、类型检查、54 项测试通过。

**在受限环境里跑 QA 脚本**：Chromium 的进程沙箱在外层沙箱内会初始化失败，Electron 随后以 `FATAL: GPU process isn't usable. Goodbye.` 崩溃（退出信号 SIGTRAP），表现为 Playwright 报 `Process failed to launch!` 或 `Target page, context or browser has been closed`。这时给四个脚本加环境变量即可：

```bash
WAGECLAW_QA_URL=http://127.0.0.1:5173 WAGECLAW_QA_NO_SANDBOX=1 node scripts/verify-pet.mjs
```

### 装饰性小窗加载失败就安静地不显示（修上一轮引入的回归）

**问题**：上一轮加的失败说明页有 440px 宽，但气泡窗只有 **290×104**、悬停浮层 **280×158** —— 塞进去会被裁成乱码，比原来的空白更糟。这不是理论推演，是用户实例的日志暴露的：开发服务器停掉期间，日志里连续出现 `ERR_CONNECTION_REFUSED` 的 `view=bubble` / `view=hover`，也就是每次播报都会新建一个气泡窗并失败。

**改动**：`DECORATIVE_VIEWS = {bubble, hover}` 加载失败就不显示，也不渲染说明页（「没出现」本就是这两类窗的正常状态）；说明页只留给需要读它的面板窗（`main` / `bootstrap` / `pet`）。窗口被 `dismiss()` 销毁后下次播报会重建，服务器恢复就自然好了。

**「加载失败」怎么判断 —— 实测出来的，不是猜的。** 一次失败加载的事件顺序：

```
did-fail-load(-102, isMainFrame=true)  79ms
dom-ready                              86ms
did-finish-load                        87ms   ← 失败时也会触发！
loadURL rejected / did-stop-loading    87ms
ready-to-show                          90ms
```

由此排除两个想当然的写法：

- **`did-finish-load` 在失败时同样触发**，不能当成功信号。
- **`webContents.getURL()` 在失败时返回的仍是「请求的 URL」**，不是 `chrome-error://`（第一版守卫就是这么写错的，被探针当场证伪）。注意这与 Playwright 的 `page.url()` 不同，后者拿到的是 `chrome-error://chromewebdata/`。

只有 `did-fail-load` 可靠，且它**先于** `ready-to-show`，所以记标志位不存在竞态。需忽略 `-3`（`ERR_ABORTED`，正常导航被新导航取代）。

**验证**（临时探针，验完即删）：用用户真实存档做 profile、自己起静态服务喂 `dist/`，中途停服制造 `ERR_CONNECTION_REFUSED`。

| 阶段 | 结果 |
| :--- | :--- |
| 服务正常（对照） | 悬停浮层 `visible: true`，五行已渲染 |
| 停服后悬停 | 窗口已创建，但 `visible: false`，未渲染 `data:` 说明页 |
| 停服后气泡 | 窗口已创建，但 `visible: false`，未渲染 `data:` 说明页 |

两个断言都先确认「窗口确实被创建过」，否则等于没测到目标路径。

### 生产包端到端验证（不只验开发服务器）

此前所有端到端验证都跑在 Vite 开发服务器上。开发服务器走的是源码模块图，**打包产物是另一条路径**（预构建、代码分割、懒加载 chunk），两者出问题的方式并不一样。补了一轮：`npm run build` 后用 `vite preview --host 127.0.0.1 --port 4173` 起静态服务，把四个 QA 脚本的 `WAGECLAW_QA_URL` 指向它重跑。

**结果**：`verify-pet.mjs`、`verify-lite.mjs`、`verify-pet-motion.mjs` 直接通过；`verify-pet-features.mjs` **失败**在悬停浮层那一段 —— `rows` 为 0，期望 5。

**定性：测试的竞态，不是产品缺陷。** `HoverView.vue` 的五行是模板里的静态节点，只要 Vue 挂载就一定存在；数到 0 说明断言跑在挂载之前。原因在生产包里 `HoverView` 是懒加载 chunk（`HoverView-*.js`，2.69 kB），`domcontentloaded` 之后才去取这个 chunk 并挂载，而开发服务器下模块图不同、时序恰好赶上了。原脚本只等 `domcontentloaded` 就立刻 `.count()`，属于「靠时序侥幸通过」。

**修法**：等首个 `.hover-row` 可见再数。

```js
await hover.waitForLoadState('domcontentloaded');
// 生产包里 HoverView 是懒加载 chunk，Vue 挂载发生在 DOMContentLoaded 之后
await hover.locator('.hover-row').first().waitFor({ state: 'visible', timeout: 8000 });
const rows = await hover.locator('.hover-row').count();
```

修完生产包与开发服务器**两侧都通过**。这条值得记：**只等 `domcontentloaded` 就做元素计数，是端到端脚本里最容易埋下的假通过**；用 Playwright 定位器自带的自动等待（`waitFor` / `expect`）而不是裸 `count()`。

### 打包版加载路径验证（`file://` 而不是 http）

打包版和开发模式加载方式不同：开发模式是 `loadURL(DEV_SERVER_URL)`（http），打包版是 `loadFile(dist/index.html, { query: { view } })`（**`file://`**）。`file://` 是独立的一套限制，开发模式下**永远不会被走到**，所以单开一轮验证。

先确认静态条件：`vite.config.ts` 里 `base: './'`，构建产物是 `<script type="module" crossorigin src="./assets/index-*.js">` —— 相对路径，可以脱离 http 根目录。

再验运行时（临时探针，验完即删）：用与 `webPreferences` 一致的窗口 `loadFile` 四个视图，等 3 秒后读 DOM。

| 视图 | 结果 |
| :--- | :--- |
| `pet` | 挂载成功（`#app` 527 字符），`canvas` 存在 |
| `hover` | 挂载成功（735 字符），**`.hover-row` 为 5** |
| `main` | 挂载成功（8122 字符） |
| `bubble` | 挂载成功（375 字符） |

**控制台与 `did-fail-load` 均为空**，只有 Electron 自带的 CSP 开发提示（该提示在打包后不再出现）。

**为什么值得单独验**：这里有两个经典的 Electron + Vite 打包坑，都可能表现为「打包后白屏」——

1. Vite 默认把资源写成绝对路径 `/assets/...`，在 `file://` 下会解析到文件系统根目录。本项目已用 `base: './'` 规避。
2. `<script type="module" crossorigin>` 是 CORS 模式的请求，而 `file://` 页面 origin 为 `null`；**动态 `import()` 的懒加载 chunk 是另一套机制**，`HoverView-*.js` 正是动态 import 出来的。两个都实测通过。

另外 `loadFile` 的 `query` 选项确认可用：`location.search` 为 `?view=pet`，`?view=` 路由在打包版下同样成立。`files` 配置包含 `dist/**/*` 与 `electron/**/*`，`app.getAppPath()` 下的 `dist/index.html` 会被打进包。
